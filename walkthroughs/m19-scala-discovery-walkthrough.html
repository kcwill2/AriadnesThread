The plugin: what Scala *is* to the pipeline

crates/lang-scala/src/plugin.rs - the modeling row of plan §3.4 and the capability row of plan:381, made code. Capabilities are not decoration: they are the gating mechanism the whole pipeline routes on (see slide 7).

crates/lang-scala/src/plugin.rs - after (new file)
fn modeling(&self) -> LanguageModeling { LanguageModeling { language: LanguageId::Scala, unit: UnitKind::SourceFile, // one .scala file = one unit aggregation: AggregationKind::PackageObject, // a package object, not a header guard: GuardKind::None, // JVM+packages dedupe; no #pragma once symbol_placement: SymbolPlacement::SingleFile, // declaring file == defining file aggregation_reexports: false, cycle_policy: CyclePolicy::TolerateWithinPackage, // mutual recursion is legal Scala external_path_markers: vec!["lib", "target", ".ivy2", ".cache"], // enforced in M20 } } /// Plan:381 literal - a `planning: true` slip is a review blocker fn capabilities(&self) -> LanguageCapabilities { LanguageCapabilities { discovery: true, dependency_graph: true, semantic_index: true, load_metric: true, planning: false, extraction: false, rewriting: false, validation: false, requires_toolchain: false, // A3: works offline, no scalac } }

Why dependency_graph: true already, when the resolver is M20? The capability says the stage is addressable for this language; the machinery arrives on schedule. The false flags on the extraction side are load-bearing today - they are what keep C++ as the sole text backend (slide 7).

The test capabilities_match_the_plan_381_literal is a full-struct assert_eq! against an independent literal - and it caught exactly the slip it was written for in an aborted implementer session.

ScalaDetector: ordering is the whole game

crates/lang-scala/src/detector.rs - mirrors FileKind::from_path's case-insensitivity. The subtle rule: basename rules run BEFORE extension rules, because build.sc (an Mill build definition) shares the .sc extension with Ammonite scripts.

crates/lang-scala/src/detector.rs - new
fn detect(&self, path: &Path) -> SourceFileKind { if is_build_definition(path) { // FIRST: build.sbt | build.sc | pom.xml return SourceFileKind::BuildDefinition; // | project/build.properties } match path.extension().and_then(|ext| ext.to_str()) { Some(ext) if ext.eq_ignore_ascii_case("scala") => SourceFileKind::Source, Some(ext) if ext.eq_ignore_ascii_case("sc") => SourceFileKind::Script, _ => SourceFileKind::Other, // .java, .kt, .cpp stay Other } }

A build.sc detected after the extension rule would silently become a "script" and vanish from build-marker logic - pinned by a dedicated test case, plus 11 more detector cases (.SCALA case-insensitivity, sub/build.properties NOT a build file, etc.).

ScalaUnitShaper: the sbt layout, as plugin knowledge

crates/lang-scala/src/shaper.rs. C++ asks the build system what its translation units are; Scala's build system (sbt) says "src/main/scala, per module". That convention now lives in the plugin, never in ariadne-build (plan rule R2).

crates/lang-scala/src/shaper.rs - new (essence)
fn build_markers(&self) -> Vec<&'static str> { vec!["build.sbt", "build.sc", "pom.xml"] // plan:383 verbatim } fn default_compiler(&self) -> &str { "scalac" } // never invoked here (A3) fn shape_units(&self, repo_root: &Path, files: &[FileRecord]) -> Vec<UnitDescriptor> { files.iter() .filter(|record| is_scala_main_source(record)) // kind == ScalaSource AND // src/main/scala present AND // src/test/scala NEVER (the tag) .map(|record| descriptor_for(record, sbt_context_name(file_dir, repo_root))) // nearest *.sbt ancestor dir names .collect() // the context; repo root => "root" }
UnitDescriptor per main file
language: Scala, unit_kind: SourceFile, context_name: "root" /* or module dir name */, build_spec/defines/include_dirs: empty // sbt invocation text is M23 toolchain work; // CompilationContext.compiler comes from // default_compiler() via build's plumbing.
Why "root" instead of the directory name?
// Test runs copy the fixture into a tempdir; // sbt's root project is named after its dir - // but the tempdir name is machine-specific. // "root" keeps assertions deterministic and // matches sbt's own root-project convention.

build_spec stays empty deliberately: kickoff must not invent a compiler command line it cannot validate offline.

D9: one registry, direction forced by the cycle rule

Before M19, two sites enumerated plugins independently (cli::registry and pipeline) - register Scala in one, and registry-aware pipeline paths silently miss it. The kickoff mandated a shared helper; the dependency graph picked the direction: cli depends on pipeline, never the reverse.

Before - duplicated enumeration
// crates/cli/src/registry.rs pub fn default_registry() -> LanguageRegistry { LanguageRegistry::new() .register(Box::new(CppPlugin::new())) } // crates/pipeline/src/lib.rs (copy #2!) pub fn default_registry() -> Arc<LanguageRegistry> { Arc::new(LanguageRegistry::new() .register(Box::new(CppPlugin::new()))) }
After - single site, both delegate
// crates/pipeline/src/lib.rs (THE site) pub fn build_default_registry() -> LanguageRegistry { LanguageRegistry::new() .register(Box::new(CppPlugin::new())) // C++ FIRST: .register(Box::new(ScalaPlugin::new())) // order = contract } // crates/cli/src/registry.rs pub fn default_registry() -> LanguageRegistry { ariadne_pipeline::build_default_registry() }

Why order is a contract: unit_shaper_for() and plugin_for() are first-wins. C++ registering first means existing C++ repos resolve to CppUnitShaper/CppPlugin exactly as before - the m00 goldens (2/2) and m1 discovery/measure witnesses prove it stayed byte-identical.

Drift lock: registries_enumerate_identical_languages (cli unit test) + d9_registries_identical (m19 cross-crate test) assert both registries agree on the language vec and the selected shaper's build markers.

The kickoff's blind spot, fixed by the plan's own mechanism

Adding a second plugin makes registry.sole_plugin() return None. Six CLI call sites (transform extractor/rewriters/validator ×2, optimize, incremental analyze) route through it and would have broken m10/m12/m14/m20 the moment Scala registered. The seams documented themselves as transitional ("per-language split lands with M19") - M19 landed the split.

Before (would break with 2 plugins)
// crates/cli/src/commands/transform.rs let registry = crate::registry::default_registry(); let text_extractor = registry .sole_plugin() // None when 2 plugins! .map(|plugin| plugin.extractor()) .ok_or_else(|| anyhow!( "no language plugin registered"))?;
After - capability-gated backend
let registry = crate::registry::default_registry(); let text_extractor = crate::registry::capability_backend(&registry, |caps| caps.extraction) // exactly-one claimant .map(|plugin| plugin.extractor()) .ok_or_else(|| anyhow!( "no language plugin registered"))?;

capability_backend resolves a stage to the one plugin whose plan:381 capability field enables it. Scala's extraction/rewriting/validation: false keep C++ the sole claimant - byte-identically for every C++ repo. No match LanguageId anywhere in handlers (rule R3); handlers stay plugin-type-free.

For incremental analysis, incremental_backend dispatches on the distinct tu.language set: one language → that plugin; an unregistered language → "unhandled language" error, never a C++ default (plan §3.3 fact 3); mixed → explicit "lands with the language-scoped cache (M21)"; zero units → old sole-plugin fallback. sole_plugin() is now fallback-only - retirement candidate at M21.

One word, and .scala became discoverable

Plan:387 claimed "crates/repo needs no functional change". False: the discovery traversal's record filter is_source_or_header() is C++-era vocabulary - ScalaSource records were impossible. The fix generalizes to repo's own neutral predicate (architect ruling, §3.1-justified, carried in the commit body):

Before - .scala never became a record
// crates/repo/src/discovery.rs:53 let kind = FileKind::from_path(&path); if kind.is_source_or_header() { // Header|Source only - files.push(FileRecord { ... }) // ScalaSource excluded! }
After
// crates/repo/src/discovery.rs:56 let kind = FileKind::from_path(&path); if kind.is_analyzable() { // Header|Source|ScalaSource - files.push(FileRecord { ... }) // .sc/build files still out, } // exactly plan:387's intent

C++ discovery is unchanged because the C++ fixtures contain no Scala files (m00/m1/m2/m18 witnesses). is_source_or_header now has zero callers - kept as pub API, retirement candidate. A co-located unit test locks the new set: a.cpp, b.h, c.scala recorded; d.sc, build.sbt not.

Impact & migration

What this changes

  • A Scala repo is now discoverable and shapeable: Repository::discover records its sources; ScalaUnitShaper yields sbt-module units with CompilationContext { "root"/module, "scalac", Scala }.
  • Registry consumers must tolerate a two-plugin default registry (it is now the normal case, not the single-plugin special case).

Breaking changes

None. All serde changes additive (no variant renames, IncludeKind::Import not yet touched); goldens byte-identical; C++ resolution order unchanged by the registration-order contract. --lang scala now passes the registration gate (previously an explicit "not registered" error).

Migration / follow-up notes

  • LanguageRegistry::sole_plugin(): fallback-only; retire when M21's language-scoped cache lands.
  • FileKind::is_source_or_header(): zero callers; retirement candidate.
  • Automatic marker-based shaper selection for mixed repos remains the deferred M18.5 gap - M19 selects the Scala shaper explicitly.
  • The deliberate models ↔ services cycle is an M20 fixture edit, to be landed as content edits (m19 pins the exact six-file record set).

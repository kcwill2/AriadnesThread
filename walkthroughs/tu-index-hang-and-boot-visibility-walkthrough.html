The Hang That Wasn't

M27 tu-index-hang-throughput + M26 boot-progress-visibility: a boot that looked frozen was a dead worker swallowed by the boot task; the killer was char-vs-byte arithmetic that panics in debug and silently wraps in release.

Field incident: 2026-10-05, a 5744-TU corpus boot frozen at 1780/5744 with ~20% CPU.
Shipped: tokenizer both-site fix + class audit + cache epoch 2.1.0; honest boot frames (path in the stage-2 row, dead boots surface as error); release-profile launch route with loud overflow checks; throughput machinery not shipped - measurement said it would be a regression.
Status: M26 CLOSED (42d4a6e). M27 fix/measurement/flag landed APPROVED; T1b bench gate still pending, PR-2-bound. See slide 16 for the honest ledger.

Executive summary (intent / scope / risk)

Intent

A two-milestone response to one incident with two independent lessons. The hang was a CONSEQUENCE: the boot worker died from a panic and the UI swallowed the death. M27 tu-index-hang-throughput kills the panic class, measures the truth, and only builds throughput machinery if the measurement justifies it. M26 boot-progress-visibility makes boot progress honest - frames from the first second, the current TU path in the stage-2 row, and a dead boot surfacing as an error, never a frozen row.

Scope landed

  • M27: tokenizer.rs both flush sites fixed + 12-site usize audit (clean) + both-profiles locks (ea21687); cache epoch 2.0.0 -> 2.1.0 as cache-wide invalidation of silently-corrupted shards (59f0512 + riders 72252a4); RELEASE-profile bench + sufficiency gate ACCEPT (bd4fb1a); release launch route + overflow-checks = true (5b517e6).
  • M26: frame-1-first boot + panic-to-error bridge (V1 f325bee); additive discovery hashing hook (V2 3f8be39); BootMilestone + TuStarted events + new_with_progress (V3 8eedb05).

Risk

Medium-low. The tokenizer hot path changed, but the fix is bit-identical on ASCII by construction and locked (test_ascii_path_tokenization_unchanged, m00/m18 parity UNEDITED). The epoch bump costs every user a full rebuild - that is the point: corrupted shards reload by design otherwise. Release binaries now pay measured ~0 steady-state cost for loud arithmetic.

The field story: E1 -> E2 -> E3

Three field measurements, eleven minutes apart, turned "indexing is slow" into a dead-worker diagnosis. All recorded in tasks/tu-index-hang-throughput-t0-evidence.md (commit 62ce72b).

E1 04:11Z - slow
Stage 2 at ~30% after 90+ minutes. 5744 TUs; counter ~1723/5744. Mean ~3.1 s/TU, single-threaded. Projection: multi-hour cold boot.
E2 04:17Z - "hang"
Counter FROZEN at 1780/5744 for several minutes. Total CPU ~20%; RAM free. UI server alive, zero build CPU.
E3 04:22Z - the specimen self-reported its death
thread 'tokio-rt-worker' (55408) panicked at crates\lang-cpp\src\tokenizer.rs:331:21: attempt to subtract with overflow

The per-core Task Manager graph at 04:21Z (8-core/16-thread Ryzen 9800X3D): several cores active, NONE pinned. That is the "worker died mid-run, siblings wind down, frozen counter" signature - not a deadlock, not a pathological TU, not I/O.

The panic line itself is evidence about the profile: overflow-checks were ON, so the user's 90-minute run was a DEBUG build. Part of "indexing takes forever" was profile, not algorithm - a fact that later killed a whole milestone of planned parallelism (slide 12). Hypotheses H-A/H-D/H-E were killed by evidence; H-B CONFIRMED as root cause; H-C survived as a throughput contributor only (t0-evidence.md sec. 5).

Why a dead worker looked like a hang

crates/cli/src/commands/ui.rs - the hole was not in the parser, it was in the boot task.

The background watcher already caught panics and logged (the ui.rs:636-673 precedent). The boot path never copied that protection: no catch_unwind, and the JoinHandle was dropped. A panic escaping the build closure left progress frozen at the last frame, state stuck "loading", the error arm never reached, the watcher never started - the server serving forever with zero build CPU. A dead boot was indistinguishable from a hung boot.

Before - the swallow (ui.rs ~:786-805, paraphrased per shape sec. 0)
let _handle = tokio::task::spawn_blocking( move || { build_ui_payload(...) // panic // escapes here }); // no catch_unwind // JoinHandle dropped // -> frozen row, state "loading", // error arm unreachable
After - drive_boot_build (live ui.rs:706-732)
match std::panic::catch_unwind( std::panic::AssertUnwindSafe(build_fn)) { Ok(Ok(out)) => { ...swap_into_state... } Ok(Err(e)) => { surface_boot_failure(state, e.to_string()); let _ = fps_tx.send(None); } Err(payload) => { let text = panic_payload_text(&*payload); surface_boot_failure(state, text.clone()); tracing::error!("UI boot task panicked: {text}"); let _ = fps_tx.send(None); } }
E3 PROVED this lock necessary independent of the arithmetic bug: the UI sat on a frozen loading row while its own worker lay dead with a truthful panic line on a console stderr nobody was watching (invariant I11). Escaped panics and Err results both write web state "error" with the failure text; the panic arm logs error! where the watcher warns - never silent (risk R8).

Root cause: the same value, two units

crates/lang-cpp/src/tokenizer.rs fix commit ea21687 (M27 T2)

The tokenizer walks a Vec<char> and advances column per CHAR (:49). At both flush sites it subtracted the run's BYTE length - while the adjacent end correctly used chars().count(). The unit inconsistency was internal to the file.

Before - byte subtracted from a char-counted column
fn flush_word(...) { let len = word.chars().count(); tokens.push(RawToken { kind: TokenKind::Word(..), line, column: column - word.len(), // :311 BYTES start, end: start + len, // :313 CHARS }); } fn flush_punct(...) { let len = punct.chars().count(); tokens.push(RawToken { kind: TokenKind::Punct(..), line, column: column - punct.len(),// :331 BYTES start, // = E3 panic site end: start + len, // :333 CHARS }); }
After - one unit for column and end (live :299-337)
fn flush_word(...) { let len = word.chars().count(); tokens.push(RawToken { kind: TokenKind::Word(..), line, column: column - len, // :311 start, end: start + len, // :313 }); } fn flush_punct(...) { let len = punct.chars().count(); tokens.push(RawToken { kind: TokenKind::Punct(..), line, column: column - len, // :331 start, end: start + len, // :333 }); }

Why this was so ugly

Any non-ASCII bytes in a word or punct run near a line start make column < byte_len, and usize underflows. In DEBUG (overflow-checks on) it panics - that is what E3 caught. In RELEASE it wraps silently: the captured pre-fix values were 18446744073709551615 (= 2 - 3, a U+20AC punct at column 1) and 10 - 11 (a word run) - huge columns flowing downstream with no panic, no log, no signal.

The fix corrects non-ASCII column values only: on ASCII paths len() == chars().count(), so the change is bit-identical by construction - locked by test_ascii_path_tokenization_unchanged in both profiles, with m00 goldens and m18 parity UNEDITED. Invariant I14 states the kill: RawToken.column stays within [1, line_chars + 1] and end - start == chars().count() under cargo test AND cargo test --release.

The M25 lesson: one-site fixes are forbidden

M25 cpp-brace-depth-underflow (CLOSED 2026-10-04 at af11113) was the same usize-underflow class: brace-depth subtraction in parser.rs, fixed site-by-site after a one-site REJECTION round. The guards landed and the class survived - the 2026-10-05 corrections memory records a runtime underflow observation still happening at parser.rs:61 during TU indexing, the same day E3 fired. That precedent wrote T2's obligation shape: both flush sites in one commit + a same-class audit; a one-site fix here would have been a plan-literal violation.

The audit (T2, dispositioned in the journal)

Every usize subtraction on position math across tokenizer.rs + parser.rs: exactly 12 sites. Disposition: FIXED x2 (the flush sites above) / SAFE-BY-INVARIANT x8 (each guard independently re-read by the reviewer, e.g. the quote_at == 0 || short-circuit at tokenizer.rs:233, the self.i >= 2 / self.i >= 3 guards, the paren_depth > 0 loop condition) / ALREADY-GUARDED x1. Zero second bugs.

parser.rs is byte-identical in the fix range - absent from the diff, the M25 floor guard at :61-69 intact and unweakened. The RED evidence stayed credible post-landing without a revert: quoted panic sites :311/:331:21 match live call-graph arithmetic, the release wrap values reproduce exactly on the pinned test sources, and the T0b hop (d6267a3) independently reproduced the corpus panic at the approved, documented-approval fixture path (tests/fixtures/m27-nonascii-underflow/ - single-encoded U+00E9 word-run and U+20AC punct-run specimens, nothing inside basic/expensive).

DP-6: the shards were already corrupt DP-6

This is the data-integrity half people forget: every artifacts/shards JSON and index written by a RELEASE build over a non-ASCII corpus - including E1's completed 30% - carries silently-wrapped columns. Post-fix, those artifacts are RELOADED, not rebuilt: the fingerprint chain hashes file content, not analyzer code, so it never self-invalidates. A correct analyzer would happily load corrupted shards forever.

Before - the reload trap
pub const CURRENT_ANALYSIS_VERSION: &str = "2.0.0"; // cache.rs:21 Fingerprint match -> shard reload Corrupted columns persist Nothing signals
After - epoch bump invalidates globally
pub const CURRENT_ANALYSIS_VERSION: &str = "2.1.0"; // cache.rs:21 ArtifactManager::check_manifest rejects the stale epoch BEFORE any blob deserialization -> forced fresh rebuild

DP-6 was a user decision (YES, 2026-10-05) because a cache-wide bump is a blunt instrument - the alternative was a named per-corpus re-index instruction with no automatic enforcement. It landed with the fix as one commit (59f0512), a single constant - shard envelope fields stay byte-identical (I7).

Ledger lesson (finding 3): the dependent set is five literal pins + one HASH pin, not the two the handoff grep found. cache.rs const + its assert, the m12 integration pin, the m27-corpus un-ignore, the m21 witness literal (a pinned "2.0.0" in tests/), and the report manifest byte-lock - an FNV hash of saved manifest bytes that embeds analysis_version while referencing no version string at all (0xddc3f9ee -> 0xbee91e36, riders 72252a4). The bump went RED twice for these; both had precedent fixes. A grep for the constant finds literal definitions only - hash pins are invisible to it.

User duty shipped with this: re-index non-ASCII corpora post-T2. The 2.1.0 bump is the only automatic invalidation; ASCII corpora need no re-index (parity proves byte-identical output).

Trade-offs - what was rejected, and why it matters

  • Rejected: the planned T3 parallelism. It was in the milestone - and the measurement killed it. The only workers capability that exists today (Some(n)) is 0.71x, i.e. slower, reproducibly (4/4 runs across two independent sessions). Dispatching T3 would have shipped a regression with a nicer progress bar. The contract stays ready for a written sufficiency FAIL; wiring before fixing the workers path is banned by the same data.
  • Rejected: auto-workers by default. min(8, available_parallelism) survives ONLY as an explicit --workers escape hatch; the default boot stays single-threaded on this evidence.
  • Rejected: fake stage-1 percent movement. The walk has no bounded total, so DiscoveryHashed holds the percent and moves only the message (I9). A counter that advances before work proportionally did is exactly the dishonesty the A4 calibration precedent exists to prevent.
  • Rejected: DP-4 repo-hash parallelism / DP-4 parse work (for now). Stage-1 measured 1.2% of cold-boot work - parallel hashing cannot move the wall. The lang-cpp parse limb stays the reserved sub-bar route, moot at the ratified bar.
  • Rejected: SSE / streaming rows. None exists; the UI polls; the web rows already mirror every frame (I6).
  • Accepted: a cache-wide epoch bump over targeted re-indexing. Blunt (everyone rebuilds once) but the only enforced invalidation - fingerprints cannot see analyzer-code corruption (slide 7).
  • Accepted: overflow-checks in release at measured ~0 steady cost. The handoff's acceptance shape was "uniform +2..+8% is fine, a stage-level cliff is not"; observed cost beat the shape.
  • Accepted deliberately: ui_smoke stays debug. It is the PR-2/bench-regime boundary; recorded on the ledger with its scope written down, per the T5 verdict's finding-3 discharge-note requirement.
The governing rule this milestone tested hard: measurement before prescription - including which profile you measure. The pre-milestone assumption ("stage 2 is slow, parallelize it") was true, irrelevant, and would have shipped a 1.41x regression, all at once.

Overview

What was implemented

  • A token contract: new themes.css (437 lines) is the single definition site for every color — 106 tokens declared identically in three parity-locked blocks (default-dark, light, dark-steampunk).
  • The sweep: ~120 color sites tokenized across styles.css, main.js, graph.js, preview.js, and index.html (including the 7 SVG arrowhead markers and inline tour styles).
  • Switching: new 61-line theme.js + anti-flash <head> bootstrap + toolbar #themeSelect, with localStorage persistence and a mandatory renderSvg() re-render.
  • Wiring: lib.rs consts, server.rs no-store routes, and export.rs standalone inlining in the correct order.
  • The gauntlet: 2 new test files plus rewired existing assertions — N-way token parity, registry↔select↔CSS-block↔bootstrap agreement, and strict-zero-literal sweeps.

Why it was needed

The UI was dark-locked: node cards, heat tiers, and arrowheads were hardcoded hexes, so a light theme was physically impossible — dark node cards on a white canvas (decision D1 overturned a test whose stated rationale was that these hexes were out of scope because they render on the canvas; the canvas is exactly the surface that must follow the theme).

Key benefits

Three shipped themes from one change; a fourth theme is one block + one option (parity tests force completeness); verdict semantics (green/amber/red, heat ramp) are structurally separated from re-tintable chrome.

The token contract D2 D3

crates/ui/assets/themes.css (new, 437 lines)

Named bg/text pairs, no color-mix

Dark-specific tints (#450a0a, #052e16, #082f49…) are surface-dependent and cannot be shared across themes. Explicit named tokens per theme are statically testable; a color-mix(in srgb, …) derivation is not — every tint is a real declaration the parity test can compare:

/* node kind cards (getNodeColors) — bg/text/border per kind */ --node-header-bg: #082f49; --node-header-text: #38bdf8; --node-header-border: #0284c7; ... --node-cycle-bg: #3b0d0d; --node-cycle-text: #fca5a5; --node-cycle-border: #ef4444; /* 5-tier collateral heat ramp (getHeatColor) — cool -> hot, always */ --heat-0-bg: #06283d; ... --heat-4-bg: #450a0a;

The specificity trick (why the default block can't be bare :root)

SPECIFICITY: the default block deliberately cannot match a themed <html> — `:root:not([data-theme])` only matches when the attribute is absent, and `:root[data-theme="dark"]` re-selects the same values when JS pins "dark" ... With this form the light/steampunk blocks win unambiguously, and a JS failure or stale attribute degrades to today's slate dark — byte-for-byte.
Single definition site enforced by test: styles.css must no longer contain :root at all. Link order is contractual too — themes.css (tokens) before styles.css (rules) — asserted in the DOM and in the export.

Three palettes, one contract

:root:not([data-theme]), :root[data-theme="dark"] { /* 106 tokens — today's slate dark, byte-for-byte */ } :root[data-theme="light"] { /* light-surface tints, every -text clears 4.5:1 */ } :root[data-theme="dark-steampunk"]{ /* warm chrome, verdicts locked */ }

Steampunk: brass chrome, locked verdicts D6 D7

Steampunk's signature color is amber — and amber already means "partly needed" in the verdict spine. Retinting verdicts for cohesion would make them indistinguishable from decoration. So the palette is split into two layers, and the split is written into the file's header:

* SEMANTIC layer — LOCKED. These hues ARE the information; do not retint them for "cohesion" in any new theme: --green / --amber / --red verdicts ... the 5-tier heat ramp (--heat-0..4-*: must always read cool -> hot) ... Rationale: steampunk's signature color is amber, and amber ALREADY means "partly needed" in the verdict spine. A steampunk cycle card must still read "cycle" via rust-red, never brass. * DECORATIVE layer — free to retint per theme: --cyan and all cyan washes/glows (D7: steampunk reuses the --cyan NAME as its brass/gaslight accent so every existing var(--cyan) call site flips to brass for free — do NOT introduce an --accent alias) ...
Decorative — retinted
/* accents — --cyan IS the brass/gaslight accent (D7); verdicts locked */ --cyan: #e6b84d; --brand-grad-a: #b45309; --brand-grad-b: #e6b84d; --edge-neutral: #7d6239; /* aged brass wire */
Semantic — byte-identical to dark
--green: #4ade80; --amber: #fb923c; --red: #ef4444; /* heat ramp tier-0 stays cool ON PURPOSE (cool -> hot is information, not style) */ --heat-0-bg: #06283d; --heat-4-bg: #450a0a;

Brass vs amber, actively disambiguated: the hypothetical preview frame moves from amber-500 #f59e0b to copper-orange --preview-amber-edge: #f97316 in steampunk, so the frame marking never reads as brass chrome. All node-kind -bg tints are genuinely warm (bronze, patina, moss) so cards don't float as cool patches. D6 is a discipline, not a mechanism — the header comment is the mitigation; no test can detect a future editor retinting the ramp.

The toolbar control D4

Reuses the .select-dark form-control idiom (D4) so it inherits the focus/hover contract already asserted for that class; a test locks the class onto the element and the option values onto the THEMES registry. Theme switching: snippet + theme.js D3

index.html <head> — the anti-flash bootstrap runs synchronously before the themed CSS paints:

<script> var bootTheme = null; try { bootTheme = localStorage.getItem('ariadne_theme'); } catch (err) { /* private mode: default */ } if (bootTheme !== 'light' && bootTheme !== 'dark' && bootTheme !== 'dark-steampunk') bootTheme = 'dark'; document.documentElement.dataset.theme = bootTheme; </script> <link rel="stylesheet" href="/themes.css"> <link rel="stylesheet" href="/styles.css">

crates/ui/assets/theme.js (new, 61 lines, loads last) owns the deferred half:

const THEMES = ['light', 'dark', 'dark-steampunk']; const DEFAULT_THEME = 'dark'; function resolveTheme(name) { return THEMES.includes(name) ? name : DEFAULT_THEME; } function applyTheme(name) { const theme = resolveTheme(name); document.documentElement.dataset.theme = theme; try { localStorage.setItem(THEME_STORAGE_KEY, theme); } catch (err) { /* Private-mode localStorage: the attribute still themes. */ } const select = document.getElementById('themeSelect'); if (select) select.value = theme; if (typeof renderSvg === 'function') renderSvg(); }
  • Why the re-render is required: node fill/stroke are baked as SVG attributes and the heat palette is recomputed per render — without renderSvg() every card keeps stale colors until the next interaction (the most likely shipped bug, called out in the plan's Risks).
  • Why the typeof guard: applyTheme must stay safe on pages where the graph assets haven't loaded.
  • Stale/unknown stored value (e.g. a theme removed in a later release) falls back to dark and the key is rewritten — <html> never carries a data-theme matching no block.
The deliberate duplication: the bootstrap hand-mirrors theme.js's read-validate-apply pair because it cannot import it — every deferred/end-of-body asset (including theme.js, which must load after graph.js to call renderSvg) loads after the themed CSS has painted. Both copies carry sync comments saying so, and test_bootstrap_theme_ids_mirror_the_theme_registry parses the snippet's quoted ids and locks them to the registry — so adding a fourth theme without mirroring fails the suite rather than silently flashing the wrong theme.

Standalone export: order matters

crates/ui/src/export.rs — a standalone report opens under file://, where /styles.css, /themes.css and /app/*.js routes do not exist. Every asset must be inlined, and a missed entry fails silently: the report just boots unthemed with no error.

// Link order is themes.css (tokens) then styles.css (rules); inlining in // the same order preserves the token-before-rule cascade for the export. let mut html = INDEX_HTML.replace( "<link rel=\"stylesheet\" href=\"/themes.css\">", &format!("<style>\n{}\n</style>", THEMES_CSS.trim_end()), ); html = html.replace( "<link rel=\"stylesheet\" href=\"/styles.css\">", &format!("<style>\n{}\n</style>", STYLES_CSS.trim_end()), ); ... ("main.js", MAIN_JS), ("theme.js", THEME_JS),
  • themes.css inlined before styles.css: same tokens-before-rules cascade as the served page — an export test asserts the token text appears before a styles.css rule in the output.
  • theme.js last in the inlining tuple: matching the served page's script order, so applyTheme() only runs once renderSvg() exists.
  • Wiring mirrored everywhere else too: lib.rs THEMES_CSS / THEME_JS include_str! consts; server.rs /themes.css + /app/theme.js routes on the existing no-store asset idiom (a cached theme bootstrap could pin a stale registry after an upgrade).

New suites (both registered in main.rs)

theme_contract.rs (409 lines) — the contract:

  • Placement: themes.css linked before styles.css; :root gone from styles.css (single definition site); theme blocks authored default-first.
  • Transport: /themes.css and /app/theme.js served with exact bytes and no-store; standalone export inlines tokens + theme.js verbatim, references neither external route, and keeps tokens ahead of rules.
  • Zero literals: styles.css and index.html carry no #hex/rgb()/rgba() outside comments (comments stripped first; &#128293;-style entities are parsed out as non-colors).
  • Four-way id agreement: <option value>s = THEMES array = [data-theme] block ids = bootstrap snippet ids — the registry is parsed from each source, so no test hardcodes a fourth copy of the theme names; half-added themes are impossible.
  • N-way token parity: every [data-theme] block must declare exactly the default block's token-name set — and it iterates the blocks found in the file, so a fourth theme is forced into parity automatically.

theme_js_zero_hex.rs (173 lines) — strict zero for main.js/graph.js/preview.js/theme.js: no raw hex (with a hand-rolled scanner that rejects &#8250; entities and url(#arrow-cycle) refs), no rgba( at all — the Phase-2b carve-outs became real tokens, so there is no exception table. Plus a declared-vs-used guard: every var(--x) in JS, styles.css, and index.html must exist in the default block (var(--x, fallback) exempt — the inline default is its own escape hatch, used for genuinely non-color vars like --source-panel-w).

Existing suites rewired through the escape hatch, exactness preserved: preview_hypothetical.rs, static_html_sections.rs, edge_verdict_story.rs, node_verdict_spine.rs, static_html.rs, and the inverted D1 test.
